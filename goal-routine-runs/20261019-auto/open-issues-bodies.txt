=== #1413 ===
**Will you contribute a fix?** Unsure — open to contributing with guidance

**Bug Summary**

Every ACP agent that Termul launches through `npx -y <pkg>@<version>` depends on npm's shared
npx cache entry for that spec (`~/.npm/_npx/<hash>/`). If that directory contains a populated
`node_modules` but **no `package.json`**, npm aborts the launch with

```
npm error code ENOENT
npm error path /home/ubuntu/.npm/_npx/4a4ca55c38a52b9f/package.json
```

and exits **254**. npx never repairs the entry, so the agent fails on every retry — and Termul
surfaces the failure as a generic `agent initialize failed: initialize timed out after 30s` or
`Incoming transport closed: {"reason":"incoming_transport_closed","method":"initialize"}`, which
gives no hint that the bootstrap is what broke.

Observed with the catalog Codex agent (`acp-registry:codex-acp` →
`npx -y @agentclientprotocol/codex-acp@2.2.2`):

| host | recorded | failure |
|---|---|---|
| Oracle Cloud ARM64 (aarch64), standalone `termul-server`, nightly 2026-10-18 | `command=npx` | npm ENOENT on `~/.npm/_npx/4a4ca55c38a52b9f/package.json`, exit 254 (7 spawn failures in ~30 min) |
| macOS 14 M1 (desktop 0.4.21 → 0.4.50) | `command=npx` | 23 × `Process exited with exit status: 254: npm error code ENOENT … /Users/insankhamil/.npm/_npx/2226a678236ff29a/package.json` (and `418c4d09cf1582a6`), 149 × `Incoming transport closed`, 126 `spawn failed` |

Once the broken entry is removed, everything works with no other change (verified below), so the
adapter package itself is healthy.

**Steps to Reproduce**

Deterministic, on Linux or macOS, no Termul UI needed:

```bash
SPEC=@agentclientprotocol/codex-acp@2.2.2
D="$HOME/.npm/_npx/4a4ca55c38a52b9f"          # the entry npx uses for that spec

# 1. healthy bootstrap (installs; the adapter then stays up, so cap it)
rm -rf "$D"; timeout 60 npx -y "$SPEC" </dev/null
ls "$D"                                       # package.json  package-lock.json  node_modules

# 2. make the entry look like the broken ones we found (populated tree, no package.json)
rm -f "$D/package.json"

# 3. every later launch now dies in npm
npx -y "$SPEC" </dev/null; echo "exit=$?"     # exit=254
#   npm error code ENOENT
#   npm error path $HOME/.npm/_npx/4a4ca55c38a52b9f/package.json

# 4. and it never self-heals — repeat step 3 as often as you like, same result.
#    The fix is to delete the entry:
rm -rf "$D"; timeout 60 npx -y "$SPEC" </dev/null; echo "exit=$?"   # 124 = the adapter came up
```

In Termul this appears as a chat that never starts: the agent process is spawned, the ACP
`initialize` never completes, and the log shows `spawn failed: kind=acp-registry:codex-acp
command=npx` with `Incoming transport closed` (or `initialize timed out after 30s`).

**Quick verification (copy-paste, no repo checkout)**

```bash
cat > /tmp/verify-codex-acp.sh <<'EOS'
#!/usr/bin/env bash
set -uo pipefail
CACHE="${1:-$HOME/.npm}"; NPX="$CACHE/_npx"; SPEC="@agentclientprotocol/codex-acp"
echo "== npx cache entries under $NPX"
for d in "$NPX"/*/; do
  [ -d "$d" ] || continue
  pj=missing; [ -f "$d/package.json" ] && pj=present
  nm=none;   [ -d "$d/node_modules" ] && nm="$(ls "$d/node_modules" | wc -l | tr -d ' ') entries"
  printf "   %-24s package.json: %-8s node_modules: %s\n" "$(basename "$d")" "$pj" "$nm"
done
echo "== what npx does now (10s cap)"
timeout 10 npx -y "$SPEC@2.2.2" </dev/null >/dev/null 2>/tmp/codex-acp-npx.err; rc=$?
echo "   exit code: $rc"; sed -n '1,4p' /tmp/codex-acp-npx.err | sed 's/^/     /'
case "$rc" in 254) echo "   -> FAIL: npm refused the cached entry";; 0|124) echo "   -> bootstrap OK";; esac
echo "== codex CLI the adapter drives"
command -v codex >/dev/null && { command -v codex; timeout 20 codex login status 2>&1 | head -1; } || echo "   codex: NOT on PATH"
echo "== termul log"
for L in "$HOME/Library/Logs/com.termul-manager.app/termul.log" "$HOME/.local/share/com.termul-manager.app/logs/termul.log"; do
  [ -f "$L" ] && { echo "   $L: $(grep -ac 'exit status: 254' "$L") × exit-254, $(grep -ac 'spawn failed.*codex-acp' "$L") × codex-acp spawn failures"; break; }
done
EOS
bash /tmp/verify-codex-acp.sh
```

Measured on our host with that script, same machine, only the cache entry changed:

```
# BROKEN (the state we found Termul stuck in)
   4a4ca55c38a52b9f         package.json: missing  node_modules: 23 entries
   exit code: 254
     npm error code ENOENT
     npm error path /home/ubuntu/.npm/_npx/4a4ca55c38a52b9f/package.json
   -> FAIL: npm refused the cached entry

# after rm -rf ~/.npm/_npx/4a4ca55c38a52b9f and one npx run
   4a4ca55c38a52b9f         package.json: present  node_modules: 23 entries
   exit code: 124            (the adapter stayed up as an ACP server)
   -> bootstrap OK
```

Also seen on this host: a second npx entry in the same broken shape — `e41f203b7505f1fb` has
`package.json: missing node_modules: none` (an empty stub), i.e. the cache holds entries created
but never completed.

**Expected**

1. **Self-heal once.** The host already has npm's stderr (`Process exited with exit status: 254:
   npm error code ENOENT …` is in the spawn-failure data). When an npx-based spawn fails with
   that signature, Termul should remove its own cache entry and retry once, then only then report
   a failure.
2. **Don't use the shared npx cache for agents at all.** Termul already owns a verified-atomic
   install root (`acp-registry-binaries`) for catalog agents; installing the adapter there and
   launching the binary directly removes this whole failure class (and the per-spawn npm cost).
3. **Say what broke.** `initialize timed out after 30s` / `Incoming transport closed` hides an
   npm bootstrap error that is right there in the captured stderr — surfacing the first stderr
   line in the chat/error state would have made this a one-minute diagnosis instead of a
   three-day one.

**Environment**

- **Linux aarch64** — Oracle Cloud Ampere, Ubuntu 24.04.5 LTS, kernel 7.0.0-1013-oracle,
  2 vCPU / 12 GB; standalone `termul-server` `0.5.0-nightly.20261018.ef9296d` (aarch64 asset,
  sha256 `47278580b7b4800192ffeb5fecba305ec60fe9696f97a485b481ec8172a1c871`) under systemd
  (loopback + web auth token); Node v26.7.0, npm 11.19.0. The same behaviour on stable v0.4.50
  (`ae1c10acfa9ad9e31ae623a68b61015b0192182221e332f8f650911590f32858`).
- **macOS 14 (M1)** — desktop app `v0.4.21` → `v0.4.50`, `macos aarch64`, log
  `~/Library/Logs/com.termul-manager.app/termul.log`.
- Agent in both cases: catalog Codex (`acp-registry:codex-acp`, `npx -y
  @agentclientprotocol/codex-acp@2.2.2`).

}

**Additional Context**

- A third machine shows a *different* proximate cause with the same user-visible symptom, worth
  checking separately: on an Arch/Omarchy desktop the failing spawn is logged as
  `kind=acp-registry:codex-acp command=true` — the command is the no-op binary `true`, so the ACP
  transport closes instantly (23 × `Incoming transport closed`, 0 × exit-254/ENOENT). That is a
  config-level command (`true`) rather than the npx cache, but it is reported the same opaque way.
- On the standalone server the adapter still cannot work after the cache fix in our deployment
  because the `codex` CLI itself is not installed there (`codex: command not found`); that is a
  prerequisite, not part of this defect.
- Workaround we use meanwhile: clear the broken npx entry (`rm -rf ~/.npm/_npx/<hash>`), or
  install the adapter once (`npm i -g @agentclientprotocol/codex-acp@2.2.2`) and point the agent
  config at that binary.

## Problem

`get_valid_token` (`src-tauri/src/acp/mcp_oauth.rs:207`) deletes the stored MCP OAuth token on any refresh failure, and nothing makes sure only one refresh runs per server at a time.

- Scenario: a warm-pool `session/new` and a user chat start together, or several chats reopen at startup, while the token is expired, and the server issues single-use refresh tokens. Chat A refreshes and stores the new token. Chat B sends the old refresh token, gets `invalid_grant`, and deletes A's new token. The next chat must sign in again.

- After #1355, `session/new`, load and resume wait for the refresh, one server at a time (`src-tauri/src/acp/manager/gates.rs:61`). rmcp times out each OAuth request at 30 s, and discovering the auth server's endpoints takes several requests. ## Fix

- Delete the token only on `AuthorizationRequired` or `TokenRefreshRejected`. Keep it on network errors.
- Bound the refresh with a short `tokio::time::timeout` and continue the chat without the token if it expires.

=== #823 ===
# P2: backend-owned durable Prompt Queue + resume hardening

Follows #821 (P0) and the P1 issue (permission auto-accept + model discovery). Third of three planned sequential PRs: P0 (#821) → P1 → P2 (this issue).

## Problem or Opportunity

### 1. The prompt queue lives only in the renderer

Queued prompts are held in the zustand store (`src/renderer/stores/prompt-queue-orchestration.ts`: `appendQueuedPrompt`, `dropPromptQueueForSession`, `buildRecoverPromptToQueuePatch`). Consequences:

- A renderer reload (desktop) or web-client reconnect over the WS relay **loses every queued prompt** — the queue is not part of any durable state.
- Two clients attached to one session cannot see each other's queued prompts.
- The P0 steering fallback (#821) deliberately reuses this renderer queue; that is acceptable for P0, but any multi-device or durability goal requires the queue to be host-owned.

### 2. Resume edge cases

- `session/load` can be rejected with `-32015` (the session is still held by another process). The current reopen path (`run_session_reopen` in `src-tauri/src/acp/manager/reopen.rs`) stringifies the error into a banner; there is no fresh-session fallback, so the user is left with a chat that cannot reopen.
- After a successful `session/load`, the local doc already holds the history; the replay window must drain without duplicating messages.
- Persisted history can contain a **stale user message without a reply** (observed with Devin). On the next prompt, the agent can answer two prompts at once; this needs a fixture test so the reconcile path is pinned.

## Proposed Solution

### 1. Backend-owned prompt queue ledger (zeron chat2 pattern)

- Append-only ledger in the Rust backend, per session: entries `{ queueId, blocks, displayBlocks?, createdAt, deviceId }`; **host-only outcomes** (`sent`, `dropped`, `superseded`); **dedupe by `queueId`** so a reconnect replay can never double-send; entries TTL-expire.
- Tauri commands + WS relay methods: `acp_queue_prompt`, `acp_queue_cancel`, queue listing; every mutation fans out an event so all clients (desktop + web) render the same queue.
- A turn-idle hook in the manager flushes the head of the queue as the next `session/prompt` (turn-boundary delivery — the same delivery contract as today's renderer queue).
- The renderer store becomes a projection: the `QueuedPrompt` shape stays, but the source of truth moves behind `acp-api` (`src/renderer/lib/acp-api.ts`).

### 2. Resume hardening

- On `-32015` from `session/load`: fall back to a fresh session in the same cwd — the history doc stays attached and is marked as continued; the user never ends up with a dead chat.
- After a successful load, drain the replay history and reconcile it against the local doc (no duplicates).
- Fixture test: persisted history containing a user message with no assistant reply; the next prompt must not produce a double answer (zeron's Devin case).

## Non-goals

- Full multi-device CRDT sync (zeron's Loro CRDT + Durable Objects stack). This issue only makes the queue host-owned and durable; cross-client fan-out reuses the existing WS relay.
- Native per-CLI harnesses (the zeron exit plan stays out of scope until adapter done-status bugs actually appear).

## Acceptance criteria

- [ ] Queue a prompt, then reload the renderer (desktop) or reconnect (web): the queued prompt survives and sends at idle.
- [ ] Two clients on one session see the same queue; `queueId` dedupe prevents double-send on reconnect replay.
- [ ] `session/load` rejected with `-32015` falls back to a fresh session; the chat UI and history pointer survive.
- [ ] Fixture test: a stale user-message-without-reply in persisted history does not cause the next prompt to double-answer.

## References

- zeron chat2 durable command queue: append-only ledger, host-only outcomes, dedupe/TTL (see `docs/research/acp.md` and `chat2-sync.md` in [zeronsh/zeron](https://github.com/zeronsh/zeron)).
- Current renderer queue: `src/renderer/stores/prompt-queue-orchestration.ts`, `src/renderer/stores/acp-store/slices/session.ts` (`dropPromptQueueForSession` call sites).

=== #822 ===
# P1: permission auto-accept ordering + model discovery precedence

Follows #821 (P0: turn-lifecycle error fidelity + `_session/steering`). Second of three planned sequential PRs: P0 (#821) → P1 (this issue) → P2 (backend-owned Prompt Queue + resume fallback).

## Problem or Opportunity

Two gaps in the ACP chat permission and model surfaces:

### 1. No permission auto-accept, and no deterministic allow-pick order

Today every `session/request_permission` always surfaces the permission modal — `respondPermission` (renderer `src/renderer/stores/acp-store/slices/session.ts`) is manual-only. There is no per-session auto-approve mode, and no helper that picks an allow option deterministically. When auto-accept is added, the pick order must be:

1. `allow_always`
2. `allow_once`
3. first option

Guard rails (learned from zeron's adapter research, `docs/research/acp.md` in [zeronsh/zeron](https://github.com/zeronsh/zeron)):

- **Question-shaped detection.** A request whose options carry no `allow_*`/`reject_*` kind is a question, not an approval → route it to the input panel (AskUserQuestion flow, #411), never auto-accept it.
- **Duplicate `allow_always`.** Codex-style agents send two `allow_always` options ("Allow for Session" + a prefix-rule option). Duplicates must not be misclassified as question-shaped; pick deterministically (first wins).

Existing helpers to extend: `isAllowOption` / `pickRejectOption` in `src/renderer/components/chat/tool-call-format.ts` (the reject side already prefers the narrowest option; the allow side has no equivalent yet).

The auto-accept decision should live in the Rust manager (not the renderer) so it also applies over the web WS relay and never races the 60s permission sub-timeout (`src-tauri/src/web/permissions.rs`).

### 2. Model discovery: config-option precedence, deprecated fallback, effort-variant collapsing

Per the ACP spec, model choices should be read from the `model` **config option** (category `Model`, kind `select`); the top-level `session/new` `models` state is deprecated. Termul already derives `SessionModelState` from config options on both `session/new` (`src-tauri/src/acp/manager/command_loop.rs`) and `session/load`/`session/resume` (`events::models_from_config_options` in `src-tauri/src/acp/events.rs`, wired via `src-tauri/src/acp/manager/reopen.rs`). Remaining gaps:

- **No deprecated-`models` fallback.** When the agent advertises no `Model`-category config option, `models_from_config_options` returns `None` and the model picker renders empty — even when the agent still fills the deprecated `models` state. Add: config option is authoritative; fall back to deprecated `models` state only when the option is not advertised.
- **No effort-variant collapsing.** Agents that advertise effort variants (`model[low]` … `model[ultra]`) render as model × effort duplicate rows in the picker. Collapse the variants into one row per model plus an effort trait/subpicker, so the picker shows one entry per model.

## Proposed Solution

### 1. Permission auto-accept (backend policy)

- New per-session auto-accept policy, **off by default**, set via a Tauri command; kept next to the turn-scoped pending-permission state in the manager.

=== #821 ===
# P0: turn-lifecycle error fidelity + `_session/steering`

## Problem or Opportunity

Two gaps in the ACP agent chat turn lifecycle:

1. **JSON-RPC error fidelity is lost.** The manager collapses turn errors to `Err(String)` (`.map_err(|e| e.to_string())` in `src-tauri/src/acp/manager/command_loop.rs`), so an agent's JSON-RPC `error.code` and `error.data` never reach the renderer. Only `ACP_AUTH_REQUIRED` survives today, via a hand-tagged prefix (see `acp_err_wire_string_tags_auth_required_only` in `src-tauri/src/acp/manager/tests.rs`). A protocol error from an agent shows to the user as an opaque string.

2. **No way to talk to a running turn.** Per the ACP prompt lifecycle, a client may send `session/prompt` only after the agent reports `idle`. Termul has no steering support, so a message typed while a turn is active always queues until the turn ends. There is no protocol-legal way to nudge an agent mid-turn. The `agent-client-protocol` schema crate (1.4) has no steering types, so this requires a hand-rolled client extension — the same pattern as the existing `_session/question` extension in `src-tauri/src/acp/manager/wire.rs`.

Also missing: regression coverage for subprocess EOF around a turn. EOF after the final response must read as a clean finish, not a crash. EOF before the response must surface as a crash with code and data intact.

Reference model: [zeron](https://github.com/zeronsh/zeron) hit and fixed this same class of bugs (`docs/research/acp.md`, "Pending prompts and silence").

## Proposed Solution

This is the first of three planned sequential PRs: P0 (this issue) → P1 (permission auto-accept + model option precedence) → P2 (backend-owned Prompt Queue + resume fallback). We plan to open the PRs ourselves.

### 1. Error fidelity through the wire

- `AgentErrorEvent` gains optional `code: i64 | null` and `data: unknown` fields; the existing `message: String` stays.
- The prompt path preserves `error.code` + `error.data` from `agent_client_protocol::Error` instead of `to_string()`.
- The `ACP_AUTH_REQUIRED` prefix tagging stays for auth classification compatibility.
- WS relay and renderer: `message` stays the primary display; `code`/`data` render in the error detail view.

### 2. EOF/error regression fixture

- A fixture script under `tests/fixtures`: a fake ACP agent whose scenario is staged via an env var (echo-then-exit, die-mid-turn, error-with-data, steering-capable).
- Tests: EOF after final response = clean finish; EOF before response = `acp:agent_crashed` with code/data preserved; overlapping prompt rejection (`ACP_TURN_IN_PROGRESS`); cancel grace.

### 3. `_session/steering` extension (hand-rolled)

- Detect `initialize._meta.steering.supported` (advertised by e.g. claude-agent-acp).
- While a turn is active and steering is supported: send `_session/steering` carrying `_meta.steering.idleBehavior: "promptRequired"` so a turn-end race hands the text back instead of firing an untracked turn.
- Unsupported agent → existing queue behavior (deliver at idle) — unchanged.
- On steering failure or hand-back: demote the entry to the Prompt Queue; the visual state switches from "Steering" to "Queued". No message is ever lost.
- UX: two distinct visual states (chip "Steering" vs "Queued"). A steered prompt enters the transcript as a normal user message. The choice is automatic per capability; there is no user toggle.

## Non-goals

- Auto-accept permission policy (P1).
- Backend-owned Prompt Queue ledger (P2) — in this phase the steering fallback reuses the current renderer queue.

## Open questions (to confirm during implementation)

- Fixture runtime: Node script (recommended: cross-platform, keeps Windows CI green) vs bash (zeron style `fake-acp.sh`).
- Hand-back demotion UX: chip switch "Steering" → "Queued" (recommended) vs error display only.

## Acceptance criteria

- [ ] A protocol error with `code`/`data` is visible in the renderer error detail.
- [ ] Fixture-driven cargo tests cover: EOF-clean-finish, EOF-crash-with-code-data, overlap-reject, cancel-grace.
- [ ] With a steering-capable agent (e.g. claude-acp), a message sent mid-turn is delivered mid-turn and appears in the transcript as a user message.
- [ ] With a non-steering agent, behavior is unchanged (queued until idle).
- [ ] Steering failure/hand-back never loses the message.

## Glossary / ADR

- `CONTEXT.md` gained the **Steering** and **Prompt Queue** terms.
- ADR planned: `docs/adr/0002-hand-rolled-steering-extension.md` — why hand-rolled (schema 1.4 has no steering) and why queue-only was rejected (mid-turn injection impossible).

=== #362 ===
## Problem or Opportunity

The upstream ACP specification (latest RFc, "MCP-over-ACP") introduces a **native MCP-over-ACP transport** with a dynamic connect/disconnect lifecycle. Termul's ACP integration currently uses the older static model and is behind on three points:

1. **`mcpCapabilities` is missing the `acp` field.** The spec now defines:
   ```json
   { "capabilities": { "mcpCapabilities": { "http": false, "sse": false, "acp": true } } }
   ```
   An agent with `mcpCapabilities.acp === true` can handle MCP servers declared with `"type": "acp"` natively. Termul's renderer type (`src/renderer/lib/acp-api.ts:74`) only models `{ http?, sse? }` — **no `acp` field**, so the capability is parsed away / invisible.

2. **No `type: "acp"` MCP server transport.** The renderer's `McpServer` variants are `stdio` / `http` / `sse` (`src/renderer/lib/acp-api.ts:177-198`, `src/renderer/lib/acp-mcp-persistence.ts`). The spec's `"type": "acp"` transport (which references another ACP component by `id`/`name`, no subprocess) is not modeled, so a user cannot add an ACP-transport MCP server.

3. **No `mcp/connect` / `mcp/disconnect` lifecycle.** The spec defines dynamic MCP connection management:
   ```json
   // mcp/connect → returns connectionId
   { "method": "mcp/connect", "params": { "acpId": "550e8400-...", "_meta": {} } }
   // mcp/disconnect → closes by connectionId
   { "method": "mcp/disconnect", "params": { "connectionId": "conn-123", "_meta": {} } }
   ```
   Termul only injects MCP servers statically at `session/new` time (`acp_new_session` → `manager.new_session`). There is no support for connecting/disconnecting MCP servers mid-session.

This is **not a regression** — the current static injection is still valid per spec. But agents that prefer the native ACP transport (e.g. a tool-providing ACP component running in the same app) cannot be wired up, and mid-session MCP management isn't possible.

## Proposed Solution

Adopt the MCP-over-ACP native transport and lifecycle (track as lower priority; gated on a concrete use case / agent demand).

1. **Extend the `mcpCapabilities` type** to include `acp?: boolean` (`src/renderer/lib/acp-api.ts:74`), and surface it in the capability UI (#359).

2. **Add the `type: "acp"` MCP server variant.** Model `McpServerAcp { type: "acp", name, id }` alongside stdio/http/sse in persistence and the wire types. Update `validateMcpServer` and the settings UI (when #287 lands) to let users register an ACP-transport MCP server.

3. **Implement `mcp/connect` + `mcp/disconnect` in the backend** (`src-tauri/src/acp/manager.rs`), bridged to the renderer as `acp:mcp_connected` / `acp:mcp_disconnected` events. Expose Tauri commands (e.g. `acp_mcp_connect(agent_id, session_id, acp_id)`, `acp_mcp_disconnect(connection_id)`) for mid-session management.

4. **Capability-aware routing.** When injecting an MCP server, prefer the `acp` transport when the agent advertises `mcpCapabilities.acp`; fall back to stdio/http/sse otherwise.

## Success Criteria

- [ ] `mcpCapabilities.acp` is parsed, typed, and surfaced.
- [ ] Users can register an MCP server with `type: "acp"` (name + id).
- [ ] `mcp/connect` and `mcp/disconnect` are implemented and exposed as commands/events.
- [ ] Mid-session connect/disconnect works without a full `session/new`.
- [ ] Capability-aware transport selection prefers `acp` when supported.

## Alternatives Considered

- **Keep static `session/new` injection only.** Simpler, and fine for stdio/http/sse servers that don't change. Insufficient for ACP-transport servers and mid-session tool changes. Defer this issue until there's a concrete agent/component that requires it.

## Additional Context

- Spec source: ACP "MCP-over-ACP" RFc (`docs/rfds/mcp-over-acp.mdx` in the upstream `agent-client-protocol` repo).
- Current type gap: `src/renderer/lib/acp-api.ts:74-75`.
- Related: #287 (MCP server management UI — should be built transport-agnostic so `type: "acp"` slots in), #359 (capability surfacing — `mcpCapabilities.acp`).
